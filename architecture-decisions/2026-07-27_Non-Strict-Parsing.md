# 2026-07 Non-Strict Parsing for Validation

## Decision

To be decided.

## Context

By design, a CSAF validators should support working on documents that are not fully valid. This introduces some
challenges not reflected in the current design:

- A CSAF validator has to work with documents that are not fully compliant with the standard. Tests that are 
  specific to a certain part of the document (e.g. vulnerabilities) should not be influenced by errors in 
  other parts of the document (e.g. revision history).
- During editing, CSAF documents may even be in a state where they are not syntactically valid JSON. Ideally, 
  a CSAF validator can work on these documents and report errors in the part before the syntax error.
- CSAF documents can become large (>100MB). It would be preferable if tests could be executed on streaming 
  data, without keeping the whole document in memory, and ideally with only one traversal of the document 
  for the entire validation.
- Transition to the new parsing scheme should be possible as an ongoing effort, converting one test after the 
  other while keeping the system running.

Given this project also intends to provide a CSAF library, there are further relevant requirements towards 
CSAF Libraries according to Conformance Clause 19 of CSAF 2.1:

- implements all elements as data structures conforming to the syntax and semantics defined in section 2.2, 2.3, 3, 4 and 5.
- provides for each element functions that allow to create, add, modify and delete that element.
- has a function that reads a CSAF Document into the data structure from a file system, URL, data stream.
- has a function that outputs the data structure as CSAF Document on the file system, as string, into a data stream.


The current implementation that deserialized the JSON into types generated by typify is not acceptable and has 
to be changed, because this parsing enforces a significant part of the schema and can e.g. fail due to violated 
regular expression constraints in unrelated parts of the document, making it impossible for tests to check certain 
parts of the document while others do not conform to the schema.


## Option A: Extractor-based Parsing (see csaf-rs/src/extractor)

Implement tests as a two-step approach: 

- A stream-based extraction approach to get data needed for a specific tests while traversing a JSON document
- A validation step that uses the extracted data to perform the test

✅ This approach can be applied to JSON files that do not follow the schema (as the extraction is independent 
from schema validation), and even to broken JSON files (handling the data up to the first syntax error).

✅ When all tests are implemented that way, it becomes possible to iterate through the JSON document once on 
streaming input, letting all tests collect the data required for their checks, while never keeping the whole
JSON document in memory (but only the data relevant for the selected tests).

✅ In first experiments on tests 6.2.38, compared to parsing into serde_json::Value, this reduced the execution time 
for a 31MB CSAF document from 0.16s to 0.07s and the RAM usage from ~90MB (growing with the document size) down 
to ~7MB (independent from the size of the input document).

⭕ However, this approach in itself does not fulfill the requirements that a CSAF library has to read a CSAF document
into a data structure, and allow editing it. 

⭕ Additionally, editing documents in a stream-based fashion (thinking of 
quick fixes) might be challenging, maybe using approaches such as JSON Patch.

⭕ New tests look significantly different due to the different approach taken.


✅ For incremental transition to the new approach, a mechanisms can be implemented to wire the new two-step tests to 
the existing test framework (without the performance gains of running all extractions in parallel, or supporting 
syntactically invalid JSON).


## Option B: Non-Strict Traits (see csaf-rs/src/non_strict)

Introduce non-strict traits for CSAF documents on top of serde_json::Value

- All functions return Option&lt;T&gt; (because elements may not be present in the JSON)
- Collections return an Iterator&lt;T&gt; with reference types
- Traits are no longer directly implemented by the typify types, but by reference wrappers around the types
- Traits are also implemented by reference wrappers around serde_json::Value

✅ This approach can be applied to JSON files that do not follow the schema (as the extraction is independent 
from schema validation and just navigates the serde_json::Value along the required path), and with some 
extra work even to broken JSON files (handling the data up to the first syntax error).

⭕ Working directly on data streams is not directly possible, the data stream has to be deserialized into a 
serde_json::Value (keeping the whole document in memory).

⭕ In first experiments, parsing a 31MB CSAF document needs ~90MB RAM (growing with the document size).

✅ These traits can be seen as the data structure required for a CSAF library.

✅ These traits could be extended to support editing the document, with the edits applied ot the underlying
typify types or the serde_json::Value.

✅ New tests look similar to the current tests (with some more edge cases for invalid data).


✅ To allow incremental conversion, a new non-strict trait hierarchy can be set up next to the existing traits, 
to be used by gradually more tests. Non-strict tests are based on RawValidatable&lt;T&gt;, using a reference 
wrapper around the serde_json::Value as trait implementation.


## Option C: Non-Strict Types

Introduce non-strict types and traits:

- Introduce non-strict type for CSAF documents that do not enforce constraints at parse time, and deserialize into them.
- Introduce non-strict traits on top of these types, unifying access to CSAF 2.0 and CSAF 2.1.

⭕ This approach can be applied to JSON files that do not follow the full CSAF schema, but just roughly conform to the 
structure of CSAF documents (so that they can still be expressed in the non-strict types). With some extra work, even 
broken JSON files (handling the data up to the first syntax error) could be handled. 
However, We would have to identify another type generator that creates less strict Rust types, and replace typify by that. 
Depending on the selected generator, different levels of invalid documents would be accepted.

✅ In first experiments on a 31MB CSAF document, compared to parsing into serde_json::Value, this reduced the execution 
time for from 0.16s to 0.13s and the RAM usage from ~90MB down to ~60MB.

⭕ Working directly on data streams is not directly possible, the data stream has to be deserialized into the new non-strict
types (keeping the whole document in memory).

✅ These types and traits can be seen as the data structure required for a CSAF library.

✅ These types and traits could be extended to support editing the document.

✅ New tests look similar to the current tests (with some more edge cases for invalid data).

⭕ To allow incremental conversion, a new non-strict type hierarchy and trait hierarchy can be set up next to the existing 
traits, to be used by gradually more tests. During that time, CSAF documents would be parsed both into the typify types
and the new non-strict types, to be used by different tests.
